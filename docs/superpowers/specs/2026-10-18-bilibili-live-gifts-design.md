# B 站直播送礼功能设计

日期：2026-10-18。状态：待用户批准，尚未编写功能代码。

开发分支：`codex/bilibili-live-gifts`，从用户当前分支 `codex/bilibili-danmaku-send2` 的 `41c5b5ad15300765268079ffb3c163876851960b` 创建。

## 目的与已确认需求

用户希望在 DD Monitor 看 B 站直播时，直接通过播放器的弹幕工具栏送礼，保留 B 站礼物的真实图片、名字、排版与操作习惯。

已经由用户明确的要求：

- 在颜文字按钮右侧增加礼物按钮，打开当前直播间的礼物浮窗。
- 展示接口提供的礼物 GIF 和名字，顶部显示账号剩余电池。
- 有多数量赠送选项的礼物，悬停时弹出数量小浮窗；只有单个赠送选项的礼物，点击即送出。
- 包括背包中的免费礼物，能在同一面板中查看和赠送。
- 赠送成功后，鼠标还在礼物浮窗内时保持打开；鼠标移到浮窗外时默认关闭。
- 从当前分支创建新分支开发；每个完成的改动必须有对应 commit，并更新相关测试、通过验证。
- 用户选择用文字确认方案，不需要浏览器交互稿。

下文标为“本设计提议”的细节是代理作出的具体选择，需要随整份设计一起确认，不能表述为用户已经逐项指定。

## 范围

本设计提议首版支持普通电池礼物，以及背包中当前账号、当前直播间允许赠送的礼物；保留服务端的房间分类、排序、权限与数量配置。

列表里可能包含开通大航海、装扮、红包等独立购买或互动流程。首版保留这些条目的图片、名称和服务端提示，但不通过普通送礼接口发送，明确提示“需前往 B 站网页操作”。充值、上舰购买、SC、送给连麦成员、盲盒结果动画和全屏礼物特效不在本次范围。背包操作绝不在库存不足时自动改成扣电池购买。

不新增登录体系、数据库、平台插件或外部依赖，沿用当前 Python、PySide6、requests 和账号凭据。

## 用户可见的行为

### 入口与面板

1. 工具栏顺序为输入框、颜文字、礼物、发送。礼物按钮与现有颜文字按钮尺寸一致，使用可在深浅主题下辨认的礼盒图标。
2. 仅在有效的 B 站直播间展示送礼入口；未登录点击时提示先登录，缺少 `bili_jct` 时提示重新登录。
3. 礼物浮窗锚定按钮上方，空间不足时移到下方；主窗与数量窗均限制在屏幕可用范围内。沿用现有控件主题，保留 B 站图片、名称、分类、排列与数量习惯。
4. 顶部显示“剩余电池”、刷新入口和简短状态。金额未知时显示“加载中”或“获取失败”，不显示成 0。
5. 普通礼物、服务端额外分类与“背包”可切换；普通礼物按 `position` 排列，分类按服务端位置排列，位置相同或缺失时保留返回顺序。只呈现房间列表引用的条目，不把全局配置当作可送列表。
6. 本设计提议常规尺寸为约 400×340 逻辑像素，默认五列。每格上方为 GIF，下方为名字与电池价格；背包显示拥有数量和有效期。空间不足时减少列数并滚动，长名字省略且可悬停查看全文。最终尺寸与间距留给实现者在现有播放器中验证。
7. 缺少 GIF 时使用静态图片；图片失败保留名称与价格，不能让某张图的失败导致整个列表不可用。隐藏时停止 GIF 播放和后续图片加载。
8. 再次点击礼物按钮、按 Esc、点击面板外部、切换直播间、退出或切换账号、隐藏或关闭播放器格子时，关闭主窗与数量窗。表情窗与礼物窗互斥。
9. 列表、余额、背包独立展示加载与失败状态，并可刷新；余额读取失败时仍可查看图片，付费赠送需等余额恢复。背包读取成功时可独立赠送背包礼物。

### 数量与送出

1. 使用礼物的 `count_map`、`diy_count_map`、`max_send_limit` 及房间上限，过滤无效、重复和超限数量。不能只凭固定的 1、10、100 等数字推断规则。
2. 只有单个赠送选项且不支持自定义数量的礼物，点击卡片立即送出 1 个。本设计提议不额外增加确认对话框，与用户要求的单击送出一致。
3. 有多个选项或允许自定义数量的礼物，悬停出现数量小浮窗。小浮窗显示礼物名称、数量选项、总电池和“赠送”按钮；本设计提议先选数量、再点“赠送”，点击原礼物卡片只打开或聚焦数量窗。
4. 自定义数量只在服务端允许时显示，必须为正整数且不超过服务端上限。余额不足时保留礼物可查看，禁用对应赠送动作并说明原因。
5. 背包保留独立的 `bag_id`；同一种礼物的不同到期批次不合并成一次跨批次发送。数量最多为当前包的剩余库存和服务端上限，预设数量仅保留合法项；本设计提议背包允许在合法范围输入数量。库存为 1 时可点击立即送出。
6. 已过期、房间限制不符、权限未满足的礼物显示原因，不发请求；空背包显示“背包暂无礼物”。若未知特殊条目的可送规则不能可靠判断，保留可查看但禁用赠送，不把未知状态解释为允许。
7. 请求进行中显示“赠送中”，同一账号只允许一个礼物赠送请求在途，避免连点或同时在多个格子重复提交。此限制不阻塞文字弹幕和播放。
8. 成功后显示送出结果并重新读取余额与背包；成功后的刷新失败显示“已送出，余额/背包刷新失败”，不得把已完成赠送显示成发送失败。重新打开其他格子的面板时也不能沿用赠送前的旧余额或库存。
9. 接口明确拒绝时显示服务端原因。网络超时、断连或无法解析成功响应时显示“结果未确认，请核对余额/背包后再试”，不自动重发。普通礼物失败不改成背包赠送，背包失败不改成付费赠送。

### 赠送后的关闭规则

这条规则对普通礼物与背包礼物一致。

- 每次打开主浮窗时，尚未进入“送出后移出即关闭”状态；浏览时仅移出鼠标不会自动关闭，Esc、再次点按钮和点击外部仍可关闭。
- 首次成功送出后进入该状态；鼠标还在主窗或当前数量窗内时，保留窗口以便继续送礼。
- 成功响应到达时如果鼠标已在两窗之外，直接关闭两窗；如果仍在内部，后续移出时关闭。
- 主窗、当前数量小浮窗及它们之间必要的鼠标过渡区域视为一个交互区域。移动到数量窗、按钮、滚动条或输入数量时不能误关；实现者可用短暂关闭延时消除窗口间缝隙，但不能让面板长时间滞留。
- 后续连续赠送保持这一规则；失败本身不触发“首次成功”状态。赠送在途期间不因为鼠标移出而自动隐藏；若此前已经成功过，则本次完成后再判断位置。明确的 Esc 或点击外部仍允许关闭，在途请求不会因此重发。
- 隐藏后即使异步完成，也不重新弹出窗口；下一次打开重置关闭状态。

## 已完成的接口调查与证据

调查日期：2026-10-18。读取时只输出接口状态和字段结构，没有保存或输出登录 Cookie、完整余额或个人库存。没有实际执行任何送礼 POST。

| 用途 | 接口或资料 | 已有证据 |
| --- | --- | --- |
| 房间礼物 | `GET https://api.live.bilibili.com/xlive/web-room/v1/giftPanel/roomGiftList`，`platform=pc`、`room_id` | 已实际请求房间 1713429650，返回 `code=0` |
| 电池余额 | `GET https://api.live.bilibili.com/pay/v2/Pay/myWallet`，`need_bp=1`、`need_metal=1`、`platform=pc` | 未登录返回 -101；现有登录态读取返回 `code=0`，`data.gold` 为整数 |
| 房间背包 | `GET https://api.live.bilibili.com/xlive/web-room/v1/gift/bag_list`，`room_id` | 现有登录态读取返回 `code=0`；当前空背包的 `list` 和 `gift_config` 均为 `null` |
| 电池送礼 | `POST /xlive/revenue/v1/gift/sendGold` | 已检查维护者发布的 bilibili-api-python 17.4.2 源码和参数；尚未做实际赠送验证 |
| 背包送礼 | `POST /xlive/revenue/v1/gift/sendBag`；另有 v2 接口实现资料 | 17.4.2 源码使用 v1；较新公开验证资料使用 v2，具体选用版本留给实现者核实，禁止在超时后换版本再次 POST |

礼物接口分为三个部分：

- `gift_data.room_gift_list.gold_list` 及 `silver_list` 是房间的主列表引用，包含 `gift_id`、`position`、`special`、`gift_scene`。
- `gift_data.tab_list` 提供额外分类，例如调查房间中的“粉丝团”和“航海”；每个分类有自己的条目顺序。
- `gift_config.base_config.list` 提供 ID、名字、价格、GIF、静态图、`count_map`、`diy_count_map` 和 `max_send_limit`；`gift_config.room_config` 为房间覆盖配置列表，按 ID 覆盖基础配置。

`special.is_use` 和 `special.tips` 表达当前权限；`gift_scene.pay_type=interactive_pay` 等特殊购买流程不能当作普通 `sendGold`。空列表与空分类必须正常处理，未引用的全局礼物不能出现在可送列表里。

金额使用原始整数计算：当前协议 `price / 1000` 为人民币元，仓库已有协议模型注明 `1000 = 1 元 = 10 电池`，因此礼物单价和 `gold` 余额按原始数值除以 100 展示电池。实现时用已读取字段与典型礼物交叉核对换算，测试覆盖小数电池，禁止浮点累加、向上取整或把 `bp` 等其他余额擅自相加。

送礼参数至少包括发送者 `uid`、主播 `ruid`、目标房间 `biz_id`、礼物 ID、数量、原始单价、`platform=pc`、`biz_code=live`、`csrf`、`csrf_token`。电池礼物使用 `coin_type=gold`、`bag_id=0`；背包使用该库存的真实 `bag_id`。账号 UID、主播 UID、长短房间号的转换要结合现有房间解析与登录接口，不能混淆发送者和接收者。

实现者需在计划的接口核实步骤确定最终请求版本和附加参数，可通过公开前端或维护者源码核对，再用本地 HTTP 服务和模拟响应验证一次点击只提交一次；自动验证不使用真实扣费来探测接口。没有真实送礼验证时，交付说明必须如实注明这一限制。

## 与现有代码的衔接

先参考现有实现，再增加送礼模块：

- `ddm/danmaku_send.py` 的 `DanmakuComposer` 提供按钮插入点、凭据同步、直播间切换、反馈、异步请求和生命周期处理；`EmoticonPopup` 提供锚定位置、分类、分批构建及隐藏时暂停加载的范例。
- `ddm/bili.py` 已有登录 Cookie 快照、CSRF、设备身份、房间号解析、接口错误转换和发送不自动重试的模式。送礼接口应遵循同样的凭据快照与超时规则。
- `ddm/images.py` 可参考异步缓存方式；现有 `load_pixmap` 会成为静态图片，GIF 必须保留原始动画字节，不能经静态图转换后再播放。使用 Qt 自带 `QMovie`，只播放可见页面中的礼物，隐藏、换分类或销毁时暂停/释放。
- 送礼逻辑独立于日益增大的弹幕输入控件；建议新建专门的礼物接口/状态与浮窗模块，具体文件划分留给实现者，避免无关重构。

所有网络请求在后台执行。请求携带账号、房间、目录版本和请求身份，旧账号、旧房间、已隐藏/关闭窗口的回调不能覆盖当前界面或重新打开窗口。图片完成回调同样检查当前页面。

发送者账号与目标房间在点击时捕获，在真正提交 POST 前再次确认尚未取消或切换；一旦请求已发出不能假装可撤回，也不能将响应应用到新账号。所有打开的面板共享账号级在途发送限制和余额/库存失效通知，防止一个格子花费后另一个格子继续用旧值判断。

缓存使用现有被忽略的 `cache/` 路径，分类和权限缓存按账号、房间隔离；刷新主动重新获取列表、余额和背包。只持久化图片缓存，不持久化余额、可送权限或临时赠送选择。

## 验收与测试

功能实现必须新增或更新相应自动测试，并通过相关回归后提交。本文只是设计交付，下面是后续功能必须兑现的验收契约。

### 接口、数据与并发

- 真实形状的脱敏 fixture 覆盖主列表与分类排序、房间覆盖配置、缺图、权限拒绝、未知特殊流程、空或畸形响应。
- 余额和价格换算精确，余额未知与 0 可区分，余额不足不 POST。
- `list=null` 是空背包；不同 `bag_id` 不合并；过期、数量不足、错房间或无权限库存不能发送。
- 本地 HTTP 服务检查实际表单编码、CSRF、Cookie 快照、发送者/主播/房间身份和目标端点；缺失凭据、非法数量与特殊礼物不能 POST。
- 明确拒绝、超时、断连、异常 JSON 均不自动重试，不跨接口兜底；连点和多个格子同时提交只能有一个在途请求。
- 切换账号或房间、在途关闭、目录刷新、旧响应迟到均不能污染当前状态；成功后的刷新失败不能改写成功结果。

### Qt 交互与回归

- 礼物按钮位于颜文字右侧；深浅主题、窄播放器、全屏和高 DPI 下可见可点击，不遮挡弹幕输入和已有控制。
- 使用真实 Qt 控件验证 GIF 可播放、隐藏暂停、图片失败回退、分类切换、滚动和两级窗口屏幕边界。
- 验证单个礼物点击即送；多数量礼物悬停打开、点击原卡片不扣费、选择数量后点赠送只发一次；自定义数量非法时禁止送出。
- 验证成功后鼠标仍在窗内保持、移到窗外关闭、响应到达时已在窗外立即关闭、主窗移向数量窗不误关，以及失败/在途/关闭再开等状态。
- 验证背包赠送成功后数量更新、耗尽条目消失、余额和库存跨格子失效、表情与礼物窗互斥。
- 继续通过 `dev/selfcheck_danmaku_send.py`、`dev/selfcheck_danmaku_composer.py`、`dev/selfcheck_emoticon_tabs.py`、`dev/selfcheck_bili_cookies.py`、`dev/selfcheck_repository_map.py` 及实际被改模块的其他相关自检。
- 真实服务验证以只读接口和人工可见 UI 检查为主。实际扣费赠送只能在用户明确指定房间、礼物和数量后验证；否则交付时记录尚未做真实扣费赠送。

## 留给实现者的决定

具体模块文件名、Qt 信号组织、请求调度与缓存容量、鼠标跨窗短延时、浮窗最终像素尺寸，以及普通礼物和背包端点的最终附加参数，由实现者依据现有代码及接口证据确定。不能改变以上用户行为、擅自扩大特殊购买范围，或把未经验证的赠送结果写成验证成功。

本设计批准后编写实施计划，再进入功能实现；每个完成的改动更新相关测试、执行验证并创建对应 Git commit。
